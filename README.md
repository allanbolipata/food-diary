# food-diary
Place for food tracking scripts

### `app.py`
Generates macros breakdown for a given diary JSON input file. For example:

```
$ python3 app.py data/diary/20261012.json
{'calories': 494.6, 'carbs': 39.0, 'fat': 21.8, 'protein': 34.4, ...}
```

Reads `data/food.json` and the diary JSON file directly (no database involved).

### `eaten.py`
Reads from `data/food_diary.db` and shows the meals eaten so far for a day, plus the running macro totals:

```
$ python3 eaten.py data/diary/20261012.json
```

Note: meals whose names contain "uneaten" are deliberately excluded — the file argument is only used to derive the date, the data itself comes from the database.

### `log.py`
Adds diary entries to the database and keeps the JSON files in sync:

```
$ python3 log.py add "Food Name" [weight] [--date YYYYMMDD] [--meal NAME]
$ python3 log.py day [date]
```

- `weight` is in serving units (grams per the catalog's `serving_size`); defaults to 1.
- `--meal` defaults to "Miscellaneous"; use `--meal "Uneaten Miscellaneous"` for uneaten items.
- The food must exist in the catalog; otherwise it exits with close-match suggestions.
- If `data/diary/<date>.json` contains items the database is missing, they are imported into the database and the JSON file is rewritten from the database — so `app.py` (JSON) and `eaten.py`/`trend.py` (DB) always agree.
- Foods not in the catalog are added as stub rows (no nutritional data) so the diary stays intact, matching `migrate_to_sqlite.py` behaviour.

### `trend.py`
Uses `data/food_diary.db` (`bin.db.daily_totals`) to plot daily protein, fat, carbs and calorie trends.

### `merge.py`
Creates a merged `meals.json` file from the dated JSONs in `data/diary/`.

### `data/`
Contains template jsons, as well as general jsons that are both used and unused:

### `data/food_diary.db`
SQLite database (tables: `foods`, `meals`, `meal_items`). The source of truth for `eaten.py`, `trend.py` and `log.py`. Originally built from the JSON files by `scripts/migrate_to_sqlite.py`.

### `data/diary`
All JSON files for food consumed are here. File names are by date. A `template.json` file also exists, which is what I used as a starting point for a while until I realized I ate the same thing every day so I just copied over the previous day's entries and changed the values. EFFICIENCY!
Keep in mind: `log.py` rewrites these files from the database, and edits made by hand will be picked up into the database the next time `log.py add` runs for that date.

### `data/food.json`
Contains all the nutritional facts that I've inputted for things I've consumed. Very easy to add new foods, so long as the general structure for new entries are consistent with old format. See `data/template_food.json`.

### `data/meals.json`
Combined food diary entries. Generated by `merge.py`.

### `data/estimate_hand.json`
Currently unused, but was going to be for estimating food portions and weights using the hand measurement technique when a scale was unavailable. I haven't had a chance to implement this.

### `data/template_food.json`
Template for Food JSON entries. Any new food entries that go in `data/food.json` should be in this format.

### `data/template_recipe.json`
Template for a recipe in JSON format. In the dated JSONs in `data/diary`, this is the listed in `foods` key.

### `bin/`
Directory containing some helper scripts and classes used by the apps.

### `bin/db.py`
SQLite storage layer. Provides `get_connection`, `load_day`, `load_foods`, `daily_totals` (the legacy JSON shapes are reconstructed so `bin.Food`/`bin.Recipe` keep working unchanged), plus `ensure_meal`, `add_meal_item` and `export_day_json` used by `log.py`.

### `bin/food_obj.py`
Food class, used to hold food data.

### `bin/helpers.py`
Helper scripts used by the app. Only helper script at the moment is `calc_food`, which converts values for food weights relative to the serving size.

### `bin/recipe_obj.py`
Recipe class, which combines food nutritional data based on Food objects assigned to it.

### `scripts/`
### `scripts/migrate_to_sqlite.py`
One-time migration: `data/food.json` + `data/diary/*.json` -> `data/food_diary.db`. Re-runnable and idempotent (rebuilds the database from scratch), but once the database is the source of truth you would not re-run it.
